Put an image on your website with Supabase

You've got an image. You want it on a real webpage that anyone can visit. Supabase can hold it for you — you just have to do the setup in the right order.

This guide goes through both halves: the stuff you click once in Supabase, then the code that makes the image actually appear. Copy-paste friendly, no fluff.

The 30-second mental model

Most confusion with this stuff comes from mixing up three things that sound similar. Keep them separate in your head and the rest is easy.

📦
1. The bucket

The actual file lives here. The raw pixels. Think of it as a folder in the cloud. In this guide it's called images.

📋
2. The table

A row that remembers the filename. It stores the path, not the image. Like an index card pointing at a drawer.

🔗
3. The public URL

The link you put in your HTML. This is what makes a browser actually show the image.

The bit that trips everyone up: the table does not store the URL. It stores a path — the filename relative to the bucket. You build the full URL from that path when you want to display it. We'll do exactly that in Part 2.

Part 1

Setting up Supabase

This is a one-time job. Once it's done, you never touch it again unless you want a second bucket. Do these in order — later steps depend on earlier ones.

1

Have a project

Sign in at supabase.com and either create a project or open the one you have. It takes a minute to spin up the first time.

2

Create the table

In the dashboard go to SQL Editor → New query, paste this, hit Run.

Two columns is genuinely all you need. id numbers each row automatically. path holds the filename. 

create table if not exists images (
  id   bigint generated by default as identity primary key,
  path text not null
);
3

Create the bucket

This is where the pixels go. You can click this one out (Storage → New bucket, name it images, toggle Public bucket on), or do it in SQL: 

insert into storage.buckets (id, name, public)
values ('images', 'images', true)
on conflict (id) do nothing;

The "Public bucket" toggle matters. If it's off, your image will upload fine but the URL won't load for anyone — you'll just get a broken-image icon.

4

Add the policies (the step everyone forgets)

Here's the thing nobody tells you: Supabase locks everything by default. Every table and every bucket starts with row level security (RLS) on, which means "nobody can do anything." Policies are the guest list you hand the bouncer.

Skip this and your upload fails with a row-level security policy error, even though the bucket exists and looks totally fine. 

-- let people READ files out of the bucket
create policy "anyone can read images"
on storage.objects for select
using (bucket_id = 'images');

-- let people UPLOAD files into the bucket
create policy "anyone can upload images"
on storage.objects for insert
with check (bucket_id = 'images');

-- let the page save rows in the table
alter table images enable row level security;

create policy "anyone can add image rows"
on images for insert
with check (true);

create policy "anyone can read image rows"
on images for select
using (true);

If you get "policy already exists", you've run this before — that's fine, skip it and carry on.

5

Grab your two values

Go to Project Settings → API. You need two things, and you'll paste them into your page in a second:

  • Project URL — looks like https://abcdefgh.supabase.co
  • Publishable key — starts with sb_publishable_...

Only ever use the publishable key in a webpage. There's another key called service_role (or "secret"). That one ignores every security rule you just wrote. If it ends up in your HTML, anyone can view source and delete your whole database. Publishable key in the browser. Secret key never leaves the server.

safe in browsersb_publishable_...
never in browsersb_secret_... / service_role

Part 2

Making it show up on the page

Now the fun half. There are only really four moves: upload the file → save the path → build the URL → put it in an <img> tag.

1

Your HTML skeleton

You need a way to pick a file, and somewhere to show the result. That's it. 

<input type="file" id="file" accept="image/*" />
<button id="go">Upload</button>
<p id="msg"></p>
<img id="out" width="300" />

accept="image/*" just tells the file picker to show images first. It's a hint, not security — it doesn't stop anyone picking something else.

2

Load the Supabase library

One script tag from a CDN. No npm, no build step, no node_modules. 

<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>
3

Connect to your project

Paste the two values from Step 5. This object is your remote control for everything Supabase.

const sb = supabase.createClient(
  'https://YOUR-PROJECT.supabase.co',   // Project URL
  'sb_publishable_YOUR_KEY'             // Publishable key
);
4

Upload the file into the bucket

Give the file a unique name first. If two people both upload cat.png, the second one either overwrites the first or errors out — so stick a random ID on the front. 

// make the filename safe, then make it unique
const safe = file.name.replace(/[^a-zA-Z0-9._-]/g, '-');
const path = crypto.randomUUID() + '-' + safe;
// e.g. "7dc34689-e05f-4f1d-8346-633985f339c8-moonface.png"

const { error } = await sb.storage
  .from('images')      // the bucket
  .upload(path, file); // the path inside it, and the file itself
5

Save the path in the table

Remember: the table stores the path, not the image and not the full URL. This is how you'll find the image again later — otherwise you'd have no idea what filenames exist in your bucket. 

await sb.from('images').insert({ path });
6

Turn the path into a URL

This is the step that answers "how do I actually see it?" Let the library build it so you never have to remember the format by hand. 

const { data } = sb.storage.from('images').getPublicUrl(path);

data.publicUrl;
// https://YOUR-PROJECT.supabase.co/storage/v1/object/public/images/7dc34689-...-moonface.png

Notice the shape, because this is the whole secret: 

project URL  +  /storage/v1/object/public/  +  bucket name  +  /  +  path

That middle chunk is fixed — it's always there for public files, and it's exactly the piece people leave out when they try to build the URL by hand.

7

Shove it into an <img> tag

Now it's just a normal image, same as any other on the internet.

document.getElementById('out').src = data.publicUrl;

All of it together

Save this as upload.html, drop in your two values, open it, pick an image.

<!DOCTYPE html>
<html>
<body>
  <input type="file" id="file" accept="image/*" />
  <button id="go">Upload</button>
  <p id="msg"></p>
  <img id="out" width="300" />

  <script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>
  <script>
    const sb = supabase.createClient(
      'https://YOUR-PROJECT.supabase.co',
      'sb_publishable_YOUR_KEY'
    );

    document.getElementById('go').onclick = async () => {
      const file = document.getElementById('file').files[0];
      const msg  = document.getElementById('msg');
      if (!file) { msg.textContent = 'Pick a file first.'; return; }

      // 1. unique, safe filename
      const safe = file.name.replace(/[^a-zA-Z0-9._-]/g, '-');
      const path = crypto.randomUUID() + '-' + safe;

      // 2. push the bytes into the bucket
      const { error: upErr } = await sb.storage.from('images').upload(path, file);
      if (upErr) { msg.textContent = 'Upload failed: ' + upErr.message; return; }

      // 3. remember the path in the table
      const { error: dbErr } = await sb.from('images').insert({ path });
      if (dbErr) { msg.textContent = 'File saved, but DB failed: ' + dbErr.message; return; }

      // 4. build the URL and show it
      const { data } = sb.storage.from('images').getPublicUrl(path);
      document.getElementById('out').src = data.publicUrl;
      msg.textContent = 'Done!';
    };
  </script>
</body>
</html>

Serve it over http, not by double-clicking the file. Opening it as file:///C:/... can make the browser block the request to Supabase. Any tiny local server works — python3 -m http.server in the folder is enough.

Two ways to use this on a real site

Once the image is up there, showing it on a public page is easy. Which approach you pick depends on whether the image is fixed or user-submitted.

Fixed image (a logo, a hero banner — you know the path already). Just hardcode the URL. No JavaScript needed at all: 

<img src="https://YOUR-PROJECT.supabase.co/storage/v1/object/public/images/moonface.png"
     alt="Moon face" />

Changing or user-uploaded images (a gallery). Read the paths out of the table and build the URLs in a loop: 

const { data: rows } = await sb.from('images').select('id, path');

for (const row of rows) {
  const { data } = sb.storage.from('images').getPublicUrl(row.path);

  const img = document.createElement('img');
  img.src = data.publicUrl;
  img.alt = row.path;
  document.body.appendChild(img);
}

Debugging

When it doesn't work

Almost every failure is one of these five. Match your error message and go.

"new row violates row-level security policy"

You skipped Step 4. The bucket exists, but there's no policy letting anyone write to it. Run the storage policies.

"Bucket not found"

The bucket name in your code doesn't match the real one. Names are case-sensitive and surprisingly easy to typo. Check Storage in the dashboard.

Upload works, but the image is a broken icon

Your bucket is private. Two fixes: flip it to public (Storage → your bucket → Settings → Public bucket), or keep it private and use a signed URL instead — a link with a temporary token that expires: 

const { data } = await sb.storage
  .from('images')
  .createSignedUrl(row.path, 60); // valid for 60 seconds

It works on your machine but not for other people

Usually the bucket being private, or you accidentally used a secret/service key that only works from your own setup. Also double-check you're not on localhost in a URL someone else is supposed to open.

Double slash in the URL

You wrote '/images/' + '/' + path. Supabase often copes, but it can break caching and CDN matching. Strip leading slashes from the path before gluing: 

const clean = path.replace(/^\/+/, '');
const url = project + '/storage/v1/object/public/' + bucket + '/' + clean;
Reality check

Going public without getting wrecked

Everything above is built on one assumption: anyone can upload. That's what made it simple. But the moment your page is genuinely public, "anyone can upload" means exactly what it says.

Concretely, someone who views your page source can:

  • Grab your publishable key and upload files straight to your bucket, without using your page.
  • Fill your storage with junk until you hit your plan's limit.
  • Upload huge files, or files that aren't images at all.

The one that actually ruins your week: a public bucket means every file is permanently viewable by anyone with the link, forever, no login. If you ever upload something private — an ID photo, a receipt, someone's face — it is on the open internet instantly.

If that matters, pick a lane:

Lane 1 — keep it public, but limit the damage

Fine for a portfolio, a meme wall, a class project. Cap the file size on the bucket, restrict allowed MIME types to image/*, and remember that images can contain location metadata (EXIF) your users might not want to share.

Lane 2 — real auth

Turn on Supabase Auth, then rewrite the policies so only logged-in users can insert, and only the uploader can delete their own stuff: 

create policy "logged in users can upload"
on storage.objects for insert
to authenticated
with check (bucket_id = 'images');

create policy "users delete their own files"
on storage.objects for delete
to authenticated
using (bucket_id = 'images' and owner = auth.uid());

Lane 3 — private bucket + signed URLs

Nothing is publicly readable. Every view gets a fresh expiring link. Best for anything personal, but the links die, so you can't paste one into a group chat and expect it to work tomorrow.

Rule of thumb: if you'd be embarrassed for a stranger to see the image, it does not belong in a public bucket. Decide before you upload, not after.
